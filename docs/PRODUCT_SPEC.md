# 経費精算・承認システム — プロダクト仕様書

**文書:** PRODUCT_SPEC.md  
**バージョン:** 0.2  
**ステータス:** 初期実装向け仕様

## 1. プロダクト概要

本プロダクトは、従業員が業務上の経費を申請し、上長や経理担当者が承認するための社内向けWebアプリケーションである。

経費の申請、承認、差戻し、再申請、履歴確認までを一元的に扱う。

対象は単一企業の社内利用とする。

このアプリケーションは、実務で利用されるWebシステムの構造や品質上の論点を学ぶための教材としても使用する。

ただし、実際の企業でそのまま本番運用できることを保証するものではない。

# Part 1. 要求（Why）

## 2. 背景と解決したい問題

企業の経費精算業務では、申請者、承認者、経理担当者が、それぞれ異なる立場から同じ申請を扱う。

このとき、次のような問題が発生する。

### 2.1 申請者の問題

- どの経費を申請したのか管理しにくい。
- 申請が誰の承認待ちなのかわからない。
- 申請が差し戻された理由を確認しにくい。
- 修正や再提出の手続きが煩雑である。

### 2.2 承認者の問題

- 自分が承認すべき申請を把握しにくい。
- 申請金額によって異なる承認ルールを適切に適用する必要がある。
- 申請内容を確認するための情報が不足することがある。
- 同じ申請を複数人が操作した際、誤った承認が発生する可能性がある。

### 2.3 組織の問題

- 経費申請に関する判断が属人的になりやすい。
- 不適切な権限で申請が承認されるリスクがある。
- 誰がいつ何を判断したのかを追跡しにくい。
- 承認状況や過去の経費を横断的に確認しにくい。

## 3. プロダクトの目的

本プロダクトは、以下を実現する。

### P-01. 経費申請の効率化

従業員が経費を簡単に申請でき、その状態を把握できるようにする。

### P-02. 承認業務の適正化

承認者が必要な情報を確認し、組織のルールに従って意思決定できるようにする。

### P-03. 業務ルールの一貫性

申請金額、承認者、申請状態などに応じたルールを、システムによって一貫して適用する。

### P-04. 透明性と追跡可能性

申請・承認・差戻しの過程を記録し、関係者が後から確認できるようにする。

### P-05. 業務データの整合性

不正な操作、重複操作、同時操作、処理失敗によって、経費申請の状態が矛盾しないようにする。

## 4. 成功の定義

以下の状態を実現できれば、プロダクトの初期目的を達成したと判断する。

1. 従業員が経費を登録し、申請できる。
2. 上長と経理担当者が適切な権限で承認できる。
3. 申請者と承認者が申請状況を把握できる。
4. 申請・承認の履歴を確認できる。
5. 権限違反や不正な状態遷移を防止できる。
6. 同時操作や処理失敗に対してデータの整合性を維持できる。

# Part 2. 要件（What）

要件では、システムが提供すべき能力を定義する。

具体的なUI、API、データベーステーブル、クラス構造は原則として指定しない。

## 5. 想定利用者

### 5.1 従業員（Employee）

経費を支払った本人。

自分の経費を申請し、申請状況や履歴を確認する。

### 5.2 上長（Manager）

自分の部下の経費申請を確認し、承認または差戻しを行う。

### 5.3 経理担当者（Accounting）

上長承認後、追加承認が必要な申請を確認する。

利用者が複数の役割を持つことを許容する。ただし、役割を持つことと、特定の申請を操作できることは区別する。

## 6. 機能要件

### FR-01. 認証

利用者は、組織が認めた外部認証基盤を通じてログインできる。

アプリケーションが利用者のパスワードを保持・管理する必要はない。

### FR-02. 申請の作成・編集

従業員は複数の経費明細を含む申請を作成できる。

提出前の申請は下書きとして保存・編集できる。

### FR-03. 申請の提出

従業員は申請に必要な情報を入力し、上長へ提出できる。

提出時には、申請内容が業務ルールに適合していることを確認する。

### FR-04. 上長承認

上長は、自分が承認権限を持つ申請を確認し、承認・差戻しできる。

### FR-05. 経理承認

申請内容に応じて、経理担当者による追加承認を求めることができる。

### FR-06. 差戻しと再申請

承認者は理由を記載して申請を差し戻せる。

申請者は差戻し内容を修正して再申請できる。

### FR-07. 申請一覧と詳細

利用者は、自分が閲覧権限を持つ申請を一覧・詳細で確認できる。

申請状態、申請者、期間などに応じた検索・絞り込みを行える。

### FR-08. 承認履歴

申請・承認・差戻しなどの重要な操作を記録し、適切な権限を持つ利用者が確認できる。

### FR-09. アクセス制御

利用者の役割、所属・上長関係、申請の所有者、申請状態に応じて操作権限を制御する。

### FR-10. 操作結果のフィードバック

利用者が行った操作の成功・失敗を明確に表示する。

操作できない場合には、その理由を理解できるメッセージを返す。ただし、権限外の情報は開示しない。

## 7. 非機能要件

### NFR-01. セキュリティ

認証、認可、入力検証を適切に実施する。

### NFR-02. 正確性

金額計算、承認状態、承認履歴の整合性を保証する。

### NFR-03. 信頼性

二重送信や同時更新によって、矛盾した業務データが生成されないようにする。

### NFR-04. 性能

申請や明細の件数が増加しても、一覧・詳細画面を実用的に利用できる。

### NFR-05. 保守性

業務ルールを理解・変更しやすい構造にする。

### NFR-06. テスト可能性

外部クラウドサービスへの依存を最小限にし、主要な業務フローを自動テストできる。

### NFR-07. 利用しやすさ

基本的な操作を直感的に行えること。初期バージョンのUIは日本語とする。

### NFR-08. 再現可能性

開発者がドキュメントに従ってローカル環境を構築し、同じ操作を再現できること。

# Part 3. 仕様（Expected Behavior）

以下は初期実装のための業務仕様である。

特に断りがない限り、初期バージョンにおける確定ルールとして扱う。

## 8. 経費申請の構造

一つの経費申請には以下を含める。

- 申請者
- 申請の目的
- 経費明細
- 合計金額
- 申請状態
- 作成日時
- 提出日時
- 申請・承認履歴

経費明細には以下を含める。

- 利用日
- 利用先
- 経費区分
- 利用目的
- 金額

初期バージョンでは日本円のみを扱う。

金額は正の整数円とし、小数を扱わない。

申請の合計金額は、経費明細の合計から算出する。クライアントから送信された合計金額を正しい値として信用しない。

## 9. 承認ルール

### BR-01. 金額による承認経路

申請の合計金額が50,000円以下の場合は、上長承認のみを必要とする。

50,000円を超える場合は、上長承認後に経理承認を必要とする。

したがって、

- 49,999円：上長承認のみ
- 50,000円：上長承認のみ
- 50,001円：上長承認 + 経理承認

とする。

### BR-02. 自己承認禁止

申請者本人は、上長または経理の役割を持っていても、自分の申請を承認できない。

### BR-03. 担当外承認禁止

上長は自分が担当する部下の申請のみ承認できる。

経理担当者は、経理承認待ちの申請のみ処理できる。

### BR-04. 提出済み申請の編集禁止

提出後、承認待ちの申請内容は編集できない。

差戻し後に限り、申請者が内容を修正できる。

### BR-05. 差戻し

上長および経理担当者は、理由を記載して申請を差し戻せる。

差戻し後の再提出では、上長承認からやり直す。過去の承認記録は履歴として保持するが、新しい申請サイクルで有効な承認として扱わない。

### BR-06. 承認の一意性

同じ申請段階に対する承認が重複して成立してはならない。

承認操作が競合した場合、一方の結果のみを有効とし、もう一方には競合または処理済みであることを通知する。

## 10. 申請状態と状態遷移

| 状態 | 説明 |
|---|---|
| DRAFT | 下書き |
| SUBMITTED | 上長承認待ち |
| ACCOUNTING_REVIEW | 経理承認待ち |
| RETURNED | 差戻し |
| APPROVED | 最終承認済み |

許可する主な遷移は次のとおり。

| 遷移前 | 操作 | 遷移後 |
|---|---|---|
| DRAFT | 提出 | SUBMITTED |
| SUBMITTED | 上長承認（5万円以下） | APPROVED |
| SUBMITTED | 上長承認（5万円超） | ACCOUNTING_REVIEW |
| SUBMITTED | 上長差戻し | RETURNED |
| ACCOUNTING_REVIEW | 経理承認 | APPROVED |
| ACCOUNTING_REVIEW | 経理差戻し | RETURNED |
| RETURNED | 再提出 | SUBMITTED |

これら以外の状態遷移は許可しない。

最終承認済み申請の編集・再提出・再承認はできない。

## 11. 利用者と組織の関係

- 各従業員は、初期バージョンでは最大1名の直属上長を持つ。
- 提出には、本人以外の有効な上長が割り当てられている必要がある。
- 上長が割り当てられていない従業員は、下書きを作成できるが提出はできない。
- 上長との関係はアプリケーションが管理する業務データである。
- 認証基盤に登録されたロールだけで、個別の申請に対する承認権限を判断してはならない。

## 12. 参照範囲

### 申請者

自分の申請のみ閲覧できる。

### 上長

自分が担当する部下の申請を閲覧できる。承認可能な申請と、閲覧可能な申請は区別する。

### 経理担当者

経理承認が必要な申請を閲覧できる。

ただし、自己承認は禁止する。

アプリケーションは、IDを変更するなどの直接的なAPIアクセスに対しても、このルールを守らなければならない。

## 13. 承認履歴

重要な状態変更について、以下を記録する。

- 操作者
- 操作対象
- 操作の種類
- 操作日時
- 遷移前の状態
- 遷移後の状態
- 操作時点の申請金額
- 差戻し理由などの補足情報

履歴は通常の利用者操作によって削除・改変できない。

承認状態の更新と履歴の記録は、整合性を保つ必要がある。

## 14. 重要な異常系

以下は初期バージョンから考慮する。

1. 他人の申請を閲覧・編集しようとする。
2. 担当外の上長が承認しようとする。
3. 申請者本人が自己承認しようとする。
4. 未提出の申請を承認しようとする。
5. すでに承認済みの申請を再承認しようとする。
6. 同じ申請に対する承認が同時に実行される。
7. データ更新途中で処理が失敗する。
8. 無効な金額や不完全な申請を提出する。
9. ログインセッションが失効する。
10. 申請一覧のデータ件数が増加する。

これらのケースに対して、システムは誤った業務状態を作らず、適切な結果を返すこと。

## 15. 受け入れ条件

| ID | シナリオ | 期待する結果 |
|---|---|---|
| AC-01 | 従業員が複数明細の経費申請を提出 | 正しい金額で上長承認待ちになる |
| AC-02 | 50,000円の申請を上長が承認 | 最終承認済みになる |
| AC-03 | 50,001円の申請を上長が承認 | 経理承認待ちになる |
| AC-04 | 経理担当者が追加承認 | 最終承認済みになる |
| AC-05 | 申請を差戻し、内容を修正して再提出 | 上長承認から再開される |
| AC-06 | 他人の申請を直接APIで変更 | 拒否され、データは変更されない |
| AC-07 | 申請者が自己承認を試みる | 拒否される |
| AC-08 | 同じ申請を同時に承認 | 重複承認や履歴の矛盾が生じない |
| AC-09 | 申請・承認履歴を表示 | 誰がいつ何をしたか確認できる |
| AC-10 | 大量の申請を一覧表示 | ページングが機能し、不必要な大量取得を避ける |

## 16. 初期バージョンの対象外

初期実装では以下を扱わない。

- 実際の支払い・銀行振込
- 会計システムとの連携
- 領収書画像のアップロードやOCR
- 複雑な税額計算
- 外貨・為替換算
- 複数企業のマルチテナント
- 多段階の任意承認ワークフロー設定
- 代理承認
- メール・プッシュ通知
- 従業員や組織の管理画面
- 本番環境へのデプロイメント

## 17. 設計上の判断優先順位

実装上の判断に迷う場合は、次の優先順位に従う。

1. 業務仕様の正確性
2. データの整合性
3. セキュリティと権限制御
4. 操作の追跡可能性
5. ユーザーの操作しやすさ
6. 性能
7. 実装の簡潔さ

未定義の詳細は、これらの原則に沿って合理的に設計してよい。

ただし、承認権限、金額の意味、状態遷移など、業務上の意味を大きく変える判断は、独断で仕様を変更せず確認する。
