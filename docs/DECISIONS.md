# 実装時の設計判断

1. **構成**：単一アプリのリポジトリとして、ルート直下に `backend`・`frontend`・`infra`・`compose.yaml` を配置する。仕様・設計判断・検証記録は `docs` にまとめ、起動手順はルートの `README.md` に記載する。
2. **バージョン**：Spring Boot 4.1.2 / Java 21 / Gradle Wrapper 8.14.3。安定版を固定。フロントはpackage.jsonで直接依存を固定しlockfileを管理する。
3. **認証**：Spring Security oauth2Login のBFF。固定IssuerとsubjectでDB従業員へ紐付ける。メールやIdPロールで業務権限を決めない。未登録・無効ユーザーを拒否する。
4. **CSRF**：標準のHttpSessionCsrfTokenRepositoryとBREACH対策付きトークンを使用。`GET /api/csrf`が遅延トークンを実体化してJSONで返し、SPAは変更操作ごとに再取得する。トークンをCookieやWeb Storageに保持しない。APIの未認証は401、CSRF不正は403。
5. **競合**：申請にJPAの@Versionを付与し、クライアントversionとDBの楽観ロックを両方チェック。明細は所有コレクションで親のversionに含む。状態更新をflushした後で履歴を挿入し、サービス全体を1トランザクションにする。競合・失敗時は両方ロールバックする。
6. **履歴**：作成・編集・提出・承認・差戻しを追記。変更・削除APIを提供しない。操作者名とID、遷移、金額、理由、時刻をDTOで返す。サンプルのSEED履歴は架空の初期状態であり実操作を装わない。
7. **金額・入力**：整数円long。クライアント合計は不使用。1明細10億円、100明細を入力上限としオーバーフローと過大なペイロードを避ける。下書きでは目的と明細0件を許可するが、存在する明細の不完全入力は拒否する。利用日・利用先・区分・利用目的・正の金額を要求する。
8. **参照範囲**：上長は現在の部下の全状態、経理は提出履歴がある5万円超の申請（差戻し・最終承認を含む）を閲覧する。未提出下書きは経理に見せない。差戻し後に5万円以下に減額された申請は経理の参照対象から外れる。担当関係と役割は操作時のDB値で判定する。承認権限と参照権限を分離する。
9. **一覧性能**：DB側で権限制御と検索・ページング、最大100件。明細コレクションは取得しない。申請者名はページ内のIDを一括取得しN+1を回避する。作成日時とIDの降順で順序を安定させる。日付フィルターは作成日の日本時間。
10. **テスト**：クラウド不要。通常はH2 PostgreSQLモード、環境変数で実PostgreSQLにも同じ統合テストを適用。2トランザクションをバリアで同期する競合テストと、処理失敗のロールバックテストを含む。Playwrightでは実Keycloakログインを使用する。
11. **ローカルデータ**：サンプルはlocalプロファイル専用のFlyway location。デフォルト構成に架空の業務データを挿入しない。認証情報とComposeの開発モードはローカル専用。
12. **ログアウト**：アプリセッションを破棄する。IdPのSSOセッションまで破棄するRP-Initiated Logoutは追加していない。複数アカウントの検証は独立したブラウザコンテキストで行う。
