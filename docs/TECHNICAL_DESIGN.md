**文書:** TECHNICAL_DESIGN.md

## 1. 開発方針

本システムは、ReactとSpring Bootを使ったモダンなWebアプリケーションとして開発する。

実装の詳細はAIが主体的に判断してよいが、以下を重視する。

1. プロダクト仕様書に記載された要求・要件を満たす。
2. 業務ルールを正しく実装する。
3. 認証と認可を明確に分離する。
4. データの整合性を保証する。
5. 一般的で保守しやすい実装を採用する。
6. ローカルで開発・検証できる。
7. 自動テストによって重要な振る舞いを確認できる。
8. 不必要な複雑さを導入しない。

本システムは教育用のアプリケーションである。ただし、教材であることを理由に、セキュリティやデータ整合性を軽視しない。

# 3. アーキテクチャ

## 3.1 全体構成

以下の構成を採用する。

Browser
  ↓
React SPA
  ↓ HTTP / JSON
Spring Boot
  ├── Spring Security
  ├── REST API
  ├── Business Logic
  └── Spring Data JPA
        ↓
     PostgreSQL

Spring Boot
  ↓ OpenID Connect
Keycloak

Reactは主に画面表示とユーザー操作を担当する。

Spring Bootは認証済みセッション、認可、業務処理、データの永続化を担当する。

## 3.2 認証方式

Spring BootをOIDCクライアントとする、Backend for Frontend（BFF）方式を採用する。

- Spring Securityの `oauth2Login` を使用する。
- Authorization Code Flowを利用する。
- Spring BootがOIDCのトークンを処理する。
- ブラウザにはアプリケーションのセッションCookieを使用する。
- ReactはアクセストークンやIDトークンを直接管理しない。
- ReactのlocalStorageやsessionStorageにOIDCトークンを保存しない。

ブラウザとSpring Bootの間は、同一オリジンで通信できる構成を基本とする。

## 3.3 認証プロバイダー

ローカル開発とCIではKeycloakを使用する。

将来的にはAuth0やAmazon Cognitoなどの標準OIDC対応IdPを利用する可能性がある。

特定のIdPの独自APIに業務ロジックが強く依存しないようにする。

Firebase Authenticationについては、標準OIDCクライアントとしての置き換えを前提にせず、採用時に別途連携方式を検討する。

## 3.4 認証と業務上の認可

認証基盤は「誰であるか」を確認する。

アプリケーションは「何を許可するか」を判断する。

以下はアプリケーション側で管理する。

- 従業員情報
- 上長との関係
- 経理担当者の権限
- 申請と利用者の関係
- 承認可否

認証済みであることを理由に、任意の申請の操作を許可してはならない。

ユーザー識別にはOIDCの `iss` と `sub` の組み合わせを使用する。

メールアドレスを変更不可能なユーザーIDとして扱わない。

アプリケーションのデータベースにユーザー情報を保持することは許可するが、ログイン用パスワードは保持しない。

認証済みでもアプリケーションに登録されていないユーザーには、業務データへのアクセスを許可しない。

# 4. Keycloakによるローカル認証

## 4.1 開発環境

初期のローカル実行環境は以下とする。

| コンポーネント | URL / 接続先 |
|---|---|
| React | http://localhost:5173 |
| Spring Boot | http://localhost:8080 |
| Keycloak | http://localhost:8180 |
| PostgreSQL | localhost:5432 |

最初の実装ではReactとSpring BootをホストOS上で動かし、KeycloakとPostgreSQLをDocker Composeで起動する。

これにより、OIDCのIssuer URLをブラウザとSpring Bootの両方から参照しやすくする。

将来的にSpring Bootをコンテナ化する場合は、ホスト名とIssuer URLの整合性を再設計する。

## 4.2 Keycloakの設定

KeycloakのRealmとOIDC Clientをコード管理する。

推奨する初期設定：

- Realm: `expense-training`
- Client: `expense-app`
- Client type: Confidential
- Authentication: Authorization Code Flow
- Client secret: ローカル開発用の値を環境設定から読み込む

Realm設定はJSONファイルとして保存する。

Docker Compose起動時にRealmとテストユーザーを自動インポートする。

Keycloakの管理画面で毎回手作業の設定をする必要がない状態を目指す。

Keycloakの開発モードはローカルとテスト環境に限定する。

## 4.3 テストユーザー

以下のユーザーを用意する。

| ユーザー | 業務上の役割 |
|---|---|
| employee-a | 一般従業員 |
| manager-a | employee-aの上長 |
| employee-b | 別の部署の従業員 |
| manager-b | employee-bの上長 |
| accounting-a | 経理担当者 |

各ユーザーには、ローカルテスト専用の認証情報を設定する。

Keycloakとアプリケーション側のテストユーザーの対応関係は再現可能にする。Realmで固定したユーザーIDと、アプリケーション側の初期データを整合させる。

テストユーザーがログインすると、適切な権限で業務操作を行えること。

## 4.4 ReactとSpring Bootの連携

ローカル開発ではViteのプロキシを使用する。

以下のようなリクエストをSpring Bootへ転送する。

- `/api/**`
- `/oauth2/**`
- `/login/**`
- `/logout`

OIDCのリダイレクトURIは、ブラウザから見えるURLと一致させる。

ログイン完了後はReactの画面へ戻る。

APIに対する未認証リクエストでは、原則として401応答を返し、HTMLのログイン画面をAPIレスポンスとして返さない。

ログイン開始時はブラウザをOIDC認証フローに遷移させる。

## 4.5 セッションとCSRF

- セッションCookieはHttpOnlyを使用する。
- 本番環境ではHTTPSとSecure属性を使用する。
- SameSite属性を適切に設定する。
- ログアウト時はアプリケーションのセッションを無効化する。
- 状態変更APIをCSRF攻撃から保護する。
- ReactがCSRFトークンを取得・送信する仕組みを用意する。

開発を容易にするためだけに、CSRF保護を全面的に無効化しない。

CSRFトークンの取得方法はSpring SecurityのSPA向け方式に従う。

認証後やログアウト後のトークン再取得も考慮する。

# 5. バックエンドの設計方針

## 5.1 基本方針

業務ロジックをControllerやRepositoryに過度に分散させない。

以下の関心事を分離する。

- HTTPリクエストの処理
- 入力検証
- 認証・認可
- 業務ルールの判断
- データアクセス
- エラー処理

具体的なクラス構成はAIが判断してよい。

ただし、必要以上に複雑な設計パターンやマイクロサービス構成を導入しない。

## 5.2 データ整合性

経費申請は金額と承認状態を扱うため、整合性を重視する。

- 金額には整数円を扱える型を使用する。
- 承認状態はサーバー側で判断する。
- 不正な状態遷移を拒否する。
- 承認状態と履歴の更新を整合的に扱う。
- トランザクション境界を明確にする。
- 更新競合を検知し、重複承認を防止する。

楽観ロックやデータベースロックなどの具体的な方式は、要件を満たす方法をAIが選択する。

## 5.3 認可

認可はサーバー側で実施する。

以下を区別する。

- ログインしているか
- 業務上の役割を持っているか
- 対象の申請にアクセスしてよいか
- 現在の申請状態で操作してよいか

Reactでボタンを隠すだけでは認可が成立したことにならない。

## 5.4 データアクセスと性能

- 一覧取得ではページングを実装する。
- 不要な関連データを大量取得しない。
- N+1クエリの発生を確認できるようにする。
- SQLログやクエリ実行状況を開発環境で調査できるようにする。
- 必要に応じてDTOや適切な取得クエリを使う。

JPA Entityをそのまま外部APIの契約として公開しない。

## 5.5 APIの設計

REST APIを基本とする。

以下に従う。

- HTTPメソッドを適切に使う。
- 入力検証を実施する。
- 業務エラーと予期しないシステムエラーを区別する。
- HTTPステータスコードを適切に使用する。
- 401、403、404、409などの意味を一貫して扱う。
- 内部スタックトレースや機密情報をレスポンスに含めない。

具体的なエンドポイント設計はAIが判断する。

# 6. フロントエンドの設計方針

ReactとTypeScriptでSPAを作成する。

## 6.1 UI

以下の画面を提供する。

- ログイン前の案内
- 自分の経費申請一覧
- 経費申請の作成・編集
- 経費申請の詳細
- 承認待ち一覧
- 承認・差戻し操作
- 申請・承認履歴の確認

具体的な画面分割やルーティングはAIが設計する。

## 6.2 UX

- 読み込み中の状態を表示する。
- 入力エラーを利用者が修正できるようにする。
- 送信中の重複操作を抑制する。
- 操作に成功・失敗したことを示す。
- APIエラーの内容を適切に表示する。
- 認証期限切れの場合は再ログインできるようにする。

ただし、画面上の操作制限だけに業務ルールの保証を依存させない。

## 6.3 実装方針

コンポーネントの再利用性と可読性を重視する。

ライブラリは必要なものだけ採用する。

業務上重要な判断を、フロントエンドにのみ実装してはならない。

# 7. 開発・テスト環境

## 7.1 Docker Compose

Docker Composeで少なくとも以下を起動できるようにする。

- PostgreSQL
- Keycloak

初期の開発環境では、ReactとSpring Bootは通常の開発コマンドで起動する。

すべての手順をREADMEに記載する。

## 7.2 初期データ

業務フローの動作確認ができるサンプルデータを用意する。

例：

- 下書きの申請
- 上長承認待ちの申請
- 経理承認待ちの申請
- 差戻し済みの申請
- 最終承認済みの申請
- 複数の経費明細を持つ申請
- 境界値を確認するための申請

すべて架空のデータとする。

初期データは再作成可能な形で管理する。

## 7.3 自動テスト

### 単体テスト

主に業務ルールを対象とする。

- 承認金額の境界条件
- 状態遷移
- 自己承認禁止
- 担当外承認禁止
- 申請合計金額の計算

### 統合テスト

Spring BootとPostgreSQLを組み合わせて検証する。

Testcontainersの使用を推奨する。

以下を重視する。

- データの永続化
- トランザクション
- 同時更新
- 認可
- APIエラー

### 認証テスト

Spring SecurityのOIDCログインを模擬するテストを活用する。

業務ロジックの単体テストが、Keycloakの起動を必須としないようにする。

### E2Eテスト

Playwrightを利用して、主要な業務フローを検証する。

実際のOIDCログインフローの検証にはローカルKeycloakを利用する。

外部クラウドの認証サービスに依存しない。

## 7.4 CI

GitHub Actionsを利用する。

最低限、以下を実行する。

- Javaバックエンドのビルド
- バックエンドのテスト
- TypeScriptの型チェック
- Reactアプリのビルド
- フロントエンドのテスト

主要なE2Eテストも、コンテナ化したKeycloakとPostgreSQLを利用して再現可能な構成にする。

# 9. AIによるコード生成の方針

## 9.1 基本原則

AIはPRODUCT_SPEC.mdを読み、要件を満たすソフトウェアを自律的に設計・実装する。

TECHNICAL_DESIGN.mdに定義された技術的制約を守る。

クラス設計、DB設計、API設計、Reactのコンポーネント設計はAIが判断してよい。

## 9.2 不明点への対応

要件に明記されていない詳細については、合理的な仮定を置いて実装を進める。

ただし、以下については勝手に業務仕様を変更しない。

- 金額と承認条件
- 状態遷移
- 認可のルール
- 認証方式
- データの整合性に関する保証

重要な未決定事項があれば説明する。

## 9.3 実装順序

次の順序を基本とする。

1. 開発環境とアプリケーションの初期構成
2. KeycloakとSpring Securityの認証連携
3. ドメインモデルとデータベース
4. 経費申請と承認ワークフロー
5. Reactの画面とAPI連携
6. 自動テストと異常系
7. 操作性と性能の改善
8. ドキュメントと最終検証

必要に応じて順序を調整してよい。

各段階で可能な限りビルドとテストを実行する。

## 9.4 コミット

意味のある変更単位でGitコミットを作成する。

コミットメッセージから、何を実装したのか理解できるようにする。

アプリケーション全体を一つの巨大なコミットにまとめない。

## 9.5 品質方針

最初から正しい実装を目指す。

教材として不具合を解説する可能性があるからといって、意図的に脆弱なコードや不正確な実装を本体へ混入させない。

講座用に問題のある実装を再現する場合は、別コミットまたは別ブランチで管理し、学習用であることを明記する。
